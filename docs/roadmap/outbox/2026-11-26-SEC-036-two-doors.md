# Platform handoff: two doors, three addresses, a pairing token

**Date:** 2026-11-26 · **Server item:** SEC-036 · **Depends on:** SEC-035 · **Client item waiting:** APL-065

## What the platform will offer

The front door stays on `:8788`. A second listener, `:8789`, serves tagged bearer client routes, media-token URLs, and the Apple TV pairing routes only. Cookies are ignored there, and none are set. Untagged routes are 404. HTTPS is required off the LAN.

Signed-in `GET /api/features` publishes three addresses:

- `home` — the LAN server
- `away` — the front door, for sign-in
- `app_away` — the app door, for API and media

*Proposed* capability `app_door` is `1` when this listener is available.

Settings → Devices can mint a one-time pairing token, about ten minutes, carried with the three addresses in a link. The server advertises `_projectionist._tcp` with the server name and a fingerprint. The advertisement has no secret.

`docs/REMOTE-ACCESS.md` will cover Tailscale, Cloudflare Tunnel plus Access, a reverse proxy with forward-auth, and port forwarding.

## This household

Cloudflare Access stays on the front-door hostname. A later written plan adds an app-door hostname with no Access, after the app door passes its tests. That plan is not applied with this item.

## Done when the client cares

- API and media use `home` when it answers, and `app_away` otherwise.
- Sign-in opens `away`, or `home` on the LAN.
- A QR or link from the pairing token is enough to open sign-in with the server already filled in.
- A discovered `_projectionist._tcp` service can be listed on first run.

Do not build the client until the app door and the QR flow have merged.
